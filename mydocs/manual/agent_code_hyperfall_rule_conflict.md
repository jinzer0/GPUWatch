# 위험 기반 Human Approval 정책

## 목적과 우선순위

BMAD와 Hyper-Waterfall의 방법론은 유지하고 반복적인 단계 승인을 위험 결정 승인으로 바꾼다. Human은 중요한 결정과 위험 행동을 승인하고 Agent는 허용된 Scope 내에서 실행한다.

1. 플랫폼·실행 도구의 권한 및 보안 제한
2. 작업지시자의 명시 지시와 승인된 Scope
3. `AGENTS.md`와 본 공통 승인 정책
4. 하위 매뉴얼·Skill·Workflow·템플릿 및 task 기록
5. 에이전트 기본 동작

하위 지침의 일반적인 승인/대기 문구는 본 정책으로 판단한다. 단, exact publication tuple, merge/release, 현재 OPEN 이슈 close, 사용자 작업 보호 등 명시적 권한·무결성 fence는 그대로 적용한다. 사용자 요청은 플랫폼 제한을 우회하지 못한다.

## 위험 분류와 실행 권한

| 수준 | 영향 기준과 예 | 실행 정책 |
|---|---|---|
| LOW | 오타·문서·UI 스타일/레이아웃·국소 리팩터링·단순 버그·테스트·분석·Scope 내 작은 변경 | 사전/계획 승인 없이 바로 실행, 필요한 검증 후 보고 |
| MEDIUM | 기존 아키텍처 내 기능 추가/확장·모듈 구현·다중 파일 리팩터링 | 명확한 사용자 요청 자체가 Scope 승인. 계획·구현·검증·리뷰·수정·기록·Stage 전환 자율 수행 |
| HIGH | 중대한 아키텍처/보안/인증·권한 변경·breaking API·데이터 삭제/파괴적 마이그레이션·운영 배포·중대한 외부 영향/비용·큰 Scope 확장 | 해당 위험 결정 또는 행동 직전에 명시 Human 승인. 거절된 행동은 실행하지 않음 |

파일 수·코드량·계획 토큰 수는 위험도의 근거가 아니다. 영향, 가역성, 보안, 데이터 무결성, 외부 부작용을 평가한다. LOW라는 이름이어도 위험 영향이 발견되면 HIGH 경계를 적용한다. 명확한 구현 요청에 동일 Scope 재승인을 요구하지 않는다. 분석/계획만 요청된 경우 구현 권한으로 확대하지 않는다.

HIGH 요청에는 결정, 대상, 영향, 대안, 실행 범위를 적고 같은 스레드의 승인 내용과 근거를 기존 작업 기록에 남긴다. 기존 승인이 동일 결정과 현재 대상/범위를 정확히 포함하면 BMAD와 Hyper-Waterfall에서 다시 묻지 않는다. 대상이나 Scope가 달라지면 새 결정이다. 단순 "계속 진행"은 직전에 명명한 결정에만 적용하며 publication/merge/release/close 권한으로 전파하지 않는다. 응답 부재나 headless 모드는 승인으로 간주하지 않는다.

## Checkpoint와 Approval Gate

- Checkpoint는 진행 상태, 변경 경로, 검증 명령/결과, 실패, 남은 위험, 다음 실행 컨텍스트를 기존 기록에 남기는 절차이며 응답 대기가 아니다.
- 계획 완료·실행 준비·Stage 시작/종료/전환·테스트·일반 코드 수정·검증 문서화·상태 갱신·최종 Evidence는 non-blocking Checkpoint다.
- Approval Gate는 HIGH 결정 또는 별도 게시/운영 권한 경계에만 둔다. 위험 작업이 있어도 독립적인 분석·계획·로컬 테스트·증거 기록은 계속한다.
- 계획/보고서 OID·blob·hash 검증은 무결성 Checkpoint이며 Human 승인 자체가 아니다. 기존 shell fence의 `APPROVED_*` 내부 컨텍스트 값은 검증된 Scope/기록에서 캡처할 수 있지만 publication/merge/close 등 실제 승인 입력을 Agent가 만들어서는 안 된다.
- 테스트 실패는 Scope 내에서 원인 분석→수정→재검증한다. 실패 증거도 남기되 실패를 완료로 표시하지 않는다. 반복 실패, 해결 불가능한 차단, 핵심 요구사항 충돌, Scope 밖 결정만 에스컬레이션한다.

## 역할과 작업 규모

- BMAD: 요구사항·사용자 의도·Scope·설계 결정·Acceptance Criteria와 규모에 맞는 계획. 이미 있는 계획이 진실 원천이면 참조하고 복제하지 않는다.
- Hyper-Waterfall: 실행 관리·Stage/Task 상태·실행 컨텍스트·Implementation Evidence·Verification·세션 handoff. Context Persistence를 승인 대기로 구현하지 않는다.
- LOW는 조사→수정→검증→간단한 결과 기록으로 충분하다. 새 이슈/두 계획서/별도 보고 Stage를 강제하지 않는다.
- MEDIUM은 하나의 기존 계획/Issue/작업 기록에 Scope·수용 기준·변경·검증을 남긴다. Issue가 있으면 그 번호와 기존 문서명/브랜치 규칙을 따른다. 외부 게시 권한이 없다는 이유로 안전한 로컬 실행을 막지 않는다.
- Stage 수는 복잡도·의존성·검증 단위에 따라 정하며 고정 최소 수는 없다. Scope 안의 재분할/계획 보정은 기록하고 자동 진행한다. 안전한 순차 실행을 Stage 승인을 기다리며 중단하지 않는다.
- 다음 세션은 기존 기록에서 Scope, 위험 결정/승인, 현재 상태, Evidence, 미해결 차단을 복원한다. 별도 승인 문서나 중복 산출물을 만들지 않는다.

## 유지되는 경계

Commit은 명시 요청된 경우에만 수행한다. 원격 push/PR 게시의 exact tuple, Merge/Release의 별도 권한과 검증, `pr-merge-cleanup`의 현재 OPEN 이슈 exact `updated_at` 승인/재검증을 유지한다. Merge는 이슈 close 승인이 아니고 CLOSED는 검증된 no-op이다. 사용자 작업을 revert/stash/delete하거나 Tool Permission·Hook·보안 설정을 임의 완화하지 않는다.

문서는 기존 내용을 읽고 필요한 부분만 수정한다. 공식 문서 루트/파일명 정책과 증거 무결성은 유지하되 Scope 내 위치 판단 기록은 자율 수행한다. 새 공식 루트 등 불명확한 결정은 확인한다. 사용자 데이터/부산물 정리도 삭제 권한과 소유권 확인을 지킨다.

## 정합성 시나리오

| 시나리오 | 기대 동작 |
|---|---|
| 오타 수정 / 일반 버그 수정 | 승인 없이 수정 및 테스트 |
| 명확한 기능 요청 | 같은 Scope 재승인 없이 계획·구현 |
| 일반 개발 Stage 전환 | 상태/Evidence 기록 후 자동 진행 |
| 테스트 실패 | Scope 내 자율 수정·재검증 |
| 중대한 아키텍처 변경 | 해당 설계 결정 승인, 독립 안전 작업 계속 |
| 운영 데이터 삭제 | 위험 행동 직전 대상/범위 명시 승인 |
| Scope 밖 기능 추가 | Scope 변경 승인 전 구현하지 않음 |
| 검증 문서화 | 승인 없이 기록 |
| Merge / Release | 기존 별도 권한 적용 |
